1.2. Виявлені залежності між модулями
--------------------------------------------------------------------------------
- main.tsx -> QueryClientProvider -> AuthProvider -> CartProvider -> App.
- CartProvider залежить від AuthContext (useAuth) і від queries/cart.
- AuthProvider залежить від queries/auth, які залежать від features/auth/api.
- Header -> useCart (CartContext) + useAuth (AuthContext) + ui/Input, ui/Button.
- ProtectedRoute -> AuthContext; захищає /profile та /cart.
- ProductDetailsPage -> useCart + useProductById; ProductDetails -> FavouriteButton,
  ProductPrice; FavouriteButton -> AuthContext + queries/favourite.
- ProfileUser -> useGetMe, useUpdateUser, useFavouriteItems, ProductCard.
- ProfilePet -> usePets, useCreatePet, useDeletePet, fetchSpecies (catalog API),
  AccordionPetItem, PetModal.
- ProductsList -> useProducts, ProductFilters; ProductFilters -> catalogApi
  (fetchBrands/fetchSpecies/fetchCategories) напряму, повз React Query.
- Усі захищені API-модулі (cart, favourite, pets, users/me) -> authFetch.
- Каталог (products/brands/categories/species) -> звичайний fetch без токена.
- Типи: більшість компонентів беруть типи з @/types/api, але
  features/catalog/api/catalogTypes.ts містить власну (застарілу) копію Product.

--- [M-01] React 19 скидає поля форми після невдалої валідації ---
Категорія: React / UI/UX
Критичність: Medium
Файл: src/features/auth/components/LoginForm/LoginForm.tsx:51
      src/features/auth/components/RegistrationForm/RegistrationForm.tsx:55
Що не так: форми використовують `<Box component="form" action={handleSubmit}>`
(React 19 form actions) з uncontrolled-полями. React 19 після завершення
action скидає всі uncontrolled-поля, навіть якщо валідація не пройшла.
Чому це проблема: користувач вводить логін/пароль, отримує "Password must be at
least 8 characters" — і поля вже порожні. Довелося вводити все заново. Для
форми логіну/реєстрації це поганий UX.
Умови прояву: будь-яка помилка клієнтської валідації. Відтворено: після submit
з паролем "123" обидва поля мають value "".
Рекомендація: або перейти на контрольовані поля/react-hook-form, або
використовувати `onSubmit` замість `action`, або керувати скиданням вручну
(не покладатися на автоматичний reset).
Впевненість: підтверджено (runtime).

--- [M-02] Logout робить повне перезавантаження до очищення стану ---
Категорія: React / надійність
Критичність: Medium
Файл: src/features/auth/context/AuthContext.tsx:45-54
Що не так: спочатку `queryClient.clear()`, потім `window.location.href = "/"`,
і лише після цього setState + localStorage.removeItem.
Чому це проблема: порядок крихкий і семантично неправильний: навігація
ініціюється до завершення очищення (у різних браузерах/середовищах це може
обірвати виконання), а повне перезавантаження втрачає SPA-стан і зайве
перезавантажує бандл. Також після logout неможливо показати toast/повідомлення.
Умови прояву: кожен вихід із профілю.
Рекомендація: спочатку очистити стан і localStorage, потім `navigate("/")`
через react-router; для повного скидання кешу — `queryClient.clear()`.
Впевненість: підтверджено (код).

--- [M-03] JWT (access + refresh) зберігаються в localStorage ---
Категорія: Безпека
Критичність: Medium
Файл: src/features/auth/api/authApi.ts:35-36
      src/features/auth/api/authFetch.ts:27, 37, 65
      src/features/auth/context/AuthContext.tsx:10-11
Що не так: обидва токени читаються/пишуться в localStorage, а refreshToken ще й
віддається через React-контекст.
Чому це проблема: будь-який XSS (наявний або майбутній) автоматично краде
довгоживучий refresh-токен. localStorage доступний усьому JS на домені.
Зараз XSS-векторів у коді не знайдено, тому це ризик, а не активна вразливість.
Умови прояву: компрометація будь-якого скрипта на сторінці (розширення,
залежність, XSS).
Рекомендація: у пріоритеті — httpOnly Secure SameSite cookie для refresh;
access тримати в пам'яті. Якщо це неможливо без зміни бекенду — задокументувати
ризик і мінімізувати час життя refresh. Не передавати refreshToken у контекст,
він там не потрібен.
Впевненість: підтверджено (код); рівень ризику залежить від моделі загроз.

--- [M-04] У репозиторії лежить db.json з паролями та email ---

--- [M-05] updateUser типізований як Promise<void>, але повертає тіло відповіді ---
Категорія: TypeScript / API
Критичність: Medium
Файл: src/features/auth/api/authApi.ts:81-98
Що не так: сигнатура `Promise<void>`, а в кінці `return data;` (результат
response.json()). Типізація не відображає контракт PATCH /users/{id}/, який
повертає GetCustomUser.
Чому це проблема: компілятор не бачить реального типу (json() -> any),
майбутній виклик не зможе використати оновлені дані, а помилка в контракті
не буде зловлена. Аналогічно `changeCartItemQuantity` не має return-типу.
Умови прояву: будь-яке використання результату updateUser.
Рекомендація: `Promise<GetCustomUser>` (за OpenAPI ApiUsersPartialUpdate) і
явний тип для response.json() або runtime-валідація (zod).
Впевненість: підтверджено (код + OpenAPI).

--- [M-06] Неузгоджена обробка помилок API, повідомлення бекенду втрачаються ---
Категорія: API / надійність
Критичність: Medium
Файл: src/features/auth/api/authApi.ts:29-31
      src/features/cart/api/cartApi.ts:8-10, 23-27
      src/features/catalog/api/catalogApi.ts:52-54, 65-67
      src/features/favourite/api/favouriteApi.ts:8-10
      src/features/profile/api/petApi.ts:8-10
Що не так: у різних модулях різні формати помилок ("error to authenticate user",
"faill to fetch products", `${status} ${statusText}`), тіло відповіді (JSON з
полями помилок DRF) ніколи не читається. Частина функцій спочатку робить
response.json(), а вже потім перевіряє response.ok.
Чому це проблема: користувач бачить або технічний текст, або загальне
"Failed to fetch"; причини на кшталт "username вже існує" чи "quantity must be
>= 1" не доносяться. Це ускладнює і UX, і діагностику.
Умови прояву: будь-яка помилка 4xx/5xx.
Рекомендація: єдиний apiClient/обгортка: перевіряти ok, парсити JSON-помилку,
кидати типізований ApiError(status, code, message, fieldErrors) і показувати
fieldErrors у формах. Порядок "спочатку ok, потім json()" — уніфікувати.
Впевненість: підтверджено (код).

--- [M-07] Каталог не має станів loading/error/empty; помилки retry-яться мовчки ---
Категорія: UI/UX / надійність
Критичність: Medium
Файл: src/features/catalog/components/ProductsList/ProductsList.tsx:28-37, 50-56
      src/main.tsx:21-23 (немає retry-конфігурації -> default 3)
Що не так: з useProducts беруться лише data; isLoading та isError ігноруються.
При помилці products = [], рендериться порожній список без пояснень. React Query
за замовчуванням робить 3 retry, зокрема для 404.
Чому це проблема: користувач бачить пусту сторінку замість "нічого не знайдено"

5.1. Короткий загальний стан проєкту
--------------------------------------------------------------------------------
Проєкт має зрозумілу feature-based структуру, сучасний стек (React 19,
React Query 5, MUI 9, Zod 4, React Compiler) і в цілому робочі основні
сценарії: каталог із фільтрами та пагінацією, картка товару, кошик, JWT-логін
із refresh-чергою, профіль із тваринами й обраним.

Разом з тим поточний стан не є "готовим до релізу":
  - production-збірка не проходить (2 помилки TypeScript);
  - лінт не проходить;
  - ключові помилки форм і мережі не показуються користувачу;
  - підтвердження пароля не перевіряється (реально створює акаунт з
    невідповідним паролем);
  - стан авторизації розсинхронізується після refresh;
  - частина UI-станів (loading/error/empty) відсутня;
  - є проблеми безпеки середнього рівня (пароль у console, JWT у localStorage,
    облікові дані в db.json, http-URL).

Код читабельний, але типізація послаблена (strict вимкнено), а обробка помилок
несистемна. Це створює відчуття працездатності на "щасливому шляху" і крихкість
на помилках.

5.4. Рекомендації щодо архітектури та підтримки коду

1. Єдиний API-клієнт. Замість шести копій BASE_URL і різних форматів помилок —

   ApiError). Це прибере M-05/M-06/H-05 і спростить тестування.
2. Єдине джерело істини для auth. Токени + стан користувача мають жити в
   одному місці; authFetch має повідомляти контекст про refresh/logout
   (подія або callback), а не мовчки правити localStorage.
3. Довідники через React Query. brands/species/categories — це серверний стан,
   його місце в useQuery зі staleTime, а не в useEffect. Це прибере дублювання

4. URL як стан каталогу. search/page/filters у searchParams; це виправить
   M-08 і зробить посилання відтворюваними.
5. Типізація з OpenAPI. Прибрати локальні копії Product (M-15), увімкнути
   strict, не використовувати `!`/`as` там, де можна звузити тип. Для
   відповідей API — або згенеровані типи, або zod-схеми на межі.
6. Єдина політика мутацій. Для кожної мутації: pending -> disable, success ->
   toast/invalidate, error -> toast + збереження введених даних. Зараз кожна
   фіча робить це по-різному.
7. Форми: контрольовані поля або react-hook-form + zodResolver. Це вирішує
   M-01, H-02 і дає field-level помилки.
8. Мінімальний набір тестів: схеми (pass1/pass2), authFetch (refresh, черга,
   невдача), CartContext, ProductsList (search/page), форма логіну. Плюс

   це приховало б блокер і перезаписало dist.
2. Юніт-тести / e2e-набір — у проєкті немає тестового фреймворку та тестів;
   нічого запускати.
3. Перевірка реального сценарію "протермінований access + невалідний refresh" —
   вимагала б ручного псування токенів/очікування expiry; зроблено висновок із
   коду (H-04).
4. Перевірка quantity=0 на реальному бекенді — вимагала б зміни кошика
   (мутація даних користувача); висновок зроблено з OpenAPI (min 1) і коду.
5. Перевірка мобільної верстки профілю — не виконувалася у браузері з
   мобільним viewport; висновок із `minWidth: 1000px` (M-16).
6. Перевірка поведінки Django APPEND_SLASH / ротації refresh / обов'язковості
   is_available — потребує доступу до налаштувань і коду бекенду.
7. Перевірка продуктивності (React Profiler, Lighthouse) — не виконувалася,
   щоб не виходити за межі статичного аудиту; знахідки L-02/L-08 позначені як
   локальні.
